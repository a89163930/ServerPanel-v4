## 1. 评审结论

架构是站得住的。三条主链路划分干净，HTTP 层零 SSH、动作全异步、缺失值不拿 0 冒充、kill 走白名单校验，这些都是有品味的设计，不需要重写。

粗糙感全部集中在**表现层**。同一屏里塞了 6 张等权卡片、20 多个 emoji 图标、7 种不同格式的数值写法和一条没有分级的结论列表；图表把温度和百分比、负载和流量放在同一个坐标轴上；443 个进程一行一个「结束/强杀」按钮把视觉重心全占了，而真正要看的命令名被长路径挤到截断。

结论：这不是需要重做的问题，是需要**重排信息层级、重建设计系统、重做组件规范**的问题。建议按本文第五章的 DR 清单分三批落地。

**体感评分（现状）**

| 维度 | 现状 | 目标 |
|---|---|---|
| 信息层级 | 4 | 9 |
| 一致性 | 3 | 9 |
| 数据可读性 | 4 | 9 |
| 空/错/载状态 | 2 | 8 |
| 专业观感 | 4 | 9 |
| 可访问性 | 2 | 7 |

## 5. 设计需求

需求分级用 MoSCoW：Must 本批必做，Should 强烈建议，Could 可延后，Won't 本期明确不做。

### 5.1 设计系统基线

#### DR-01 色彩 token 重整

现状 CSS 变量有 13 个，色值散在 6 处 rgba 字面量里，状态色只以 emoji 形式出现。需建立语义层。

| token | 值 | 用途 |
|---|---|---|
| `--bg-base` | `#0B0E14` | 页面底色 |
| `--bg-sunken` | `#070910` | 代码块、表格内嵌区、图表底 |
| `--bg-surface` | `#151A24` | 卡片 |
| `--bg-raised` | `#1B2230` | 弹窗、悬浮层、下拉 |
| `--border-subtle` | `#222A38` | 常规描边 |
| `--border-strong` | `#2E3849` | 选中、聚焦描边 |
| `--text-primary` | `#E4E9F2` | 主文本与主数值 |
| `--text-secondary` | `#98A4B8` | 说明、标签 |
| `--text-tertiary` | `#6B7789` | 弱化信息、占位 |
| `--accent` | `#6D8DFF` | 主操作、聚焦、选中 |
| `--accent-soft` | `rgba(109,141,255,.14)` | 选中底、图表填充 |
| `--ok` | `#35C88A` | 正常 |
| `--warn` | `#E8A33D` | 预警 |
| `--bad` | `#E5484D` | 严重 |
| `--info` | `#4CC3D9` | 信息态 |

强制规则：

1. 状态必须色与形状双编码，不得仅靠颜色区分。正常用圆点、预警用三角、严重用方块或实心条，且始终配文字标签。
2. 移除全部 emoji 图标与 emoji 状态符，改为 16px 线性内联 SVG，`stroke-width: 1.5`，颜色继承 `currentColor`。
3. 语义色只在对应语义处出现，禁止拿 warn 色当装饰。

验收：全文件 `grep` 无 emoji 字符；状态色使用处 100% 伴随文字或形状标识。

#### DR-02 字阶与数字排版

| 层级 | 字号/行高 | 字重 | 用途 |
|---|---|---|---|
| Display | 28/32 | 600 | 核心指标主值 |
| Title | 18/26 | 600 | 页面标题 |
| Section | 14/20 | 600 | 区块标题 |
| Body | 13/20 | 400 | 正文 |
| Label | 12/16 | 500 | 卡片标签、轴标签 |
| Caption | 11/16 | 400 | 次要说明 |

强制规则：

1. 所有数值启用 `font-variant-numeric: tabular-nums`，同一列数字必须等宽对齐。
2. 数值与单位分层：数值 Display，单位和占比用 Label 级 secondary 色，不与数值同字号。
3. 界面字体与图表字体统一为 `Microsoft YaHei UI, "PingFang SC", system-ui, sans-serif`，去掉图表单独用 Consolas 的设定，图表仅刻度数值用等宽。

#### DR-03 间距、圆角、栅格

1. 间距统一 4 基数，只允许 4/8/12/16/20/24/32/40。
2. 圆角三级：sm 6 控件、md 10 卡片、pill 999 胶囊与徽章。
3. 阴影仅浮层使用，卡片靠描边和背景分层，不堆阴影。
4. 内容区最大宽度不设限，但左右留白 24px，卡片间距 16px。

### 5.2 布局与信息层级

#### DR-04 总览页首屏改为「一主四辅」结构 Must

现状 5+1 栅格空洞的根因是 6 张等权卡片用 auto-fit 自动铺。改为显式结构：

```
┌─────────────────────────────────────────────────────────┐
│  GPU 主卡（大）                                          │
│  3090 · 利用率 0% · 显存 0.2/24G · 47℃ · 22W           │
│  [迷你趋势 sparkline]          [现在能开新任务吗：能]     │
└─────────────────────────────────────────────────────────┘
┌──────────┬──────────┬──────────┬──────────┐
│ CPU      │ 内存     │ 磁盘     │ 网络     │
└──────────┴──────────┴──────────┴──────────┘
┌─────────────────────────────────────────────────────────┐
│ 结论卡（一段话 + 最多 3 条要点）                          │
└─────────────────────────────────────────────────────────┘
┌────────────────────────┬────────────────────────────────┐
│ 占显存进程 / 训练任务    │ CPU 占用 Top 8                 │
└────────────────────────┴────────────────────────────────┘
```

要点：

1. GPU 提为一级对象，因为它才是这面板的判断依据。代码里结论本身就在围绕 GPU 展开。
2. GPU 主卡内嵌一条 60px 高 sparkline，用 15 分钟粒度，不需要交互。
3. GPU 主卡必须给出一句人话结论：能否直接开新训练、显存还剩多少、当前是谁占着。
4. 四张辅卡等宽等高，数值格式统一为「主数值 + 单位」，占比统一放在副行。
5. 两栏区块必须等高，左栏空时右栏不塌陷，也不允许出现 200px 高的空洞。

验收：1280px 与 1920px 宽度下均无孤儿卡片、无半屏空白；截图存档比对。

#### DR-05 结论区改为「一句话 + 要点」 Must

现状 6 行平铺绿勾。改为：

1. 首行一句结论，必须回答「现在能不能开新训练 / 有没有异常」，而不是罗列指标。
2. 次行最多 3 条要点，每条一行，按严重度排序，严重项在前。
3. 每条要点右侧挂一个可跳转的动作入口，例如跳到占用该资源的进程。
4. 无异常时用单行「一切正常」加最近一次检查时间，不铺 6 行。

#### DR-06 进程表操作按钮改为按需显露 Must

1. 「结束」「强杀」默认不渲染，行 hover 或行选中时才出现。
2. 行的操作区预留固定宽度，避免 hover 时布局跳动。
3. 「强杀」在 hover 态只显示图标 + tooltip，二次确认弹窗里必须用红色实心按钮并复述影响。
4. 单页行数从 100 降到 50，把屏幕留给更多可读信息。

#### DR-07 命令列改为「短名优先」 Must

1. 默认展示 basename 加关键参数，例如 `preprocess.py --config 中间产物/清洗流水线_20261113/preprocess_idem_twin.yaml`。
2. 完整路径通过行展开或 title 提示查看，不占用列宽。
3. 提供「显示完整路径」开关，状态持久化。

#### DR-08 挂载点列表改为带序列表 Must

1. 每行左侧是挂载点与来源设备，右侧是容量条加百分比，容量条内嵌 warn 与 bad 阈值分段。
2. 按占用率降序，占用率最高的那条置顶。
3. 阈值分段直接用 `config.json` 的告警阈值，不硬编码。

| 异常 | 数据缺失时显示「无数据」加原因，副行说明原因，禁止显示 0 |

#### DR-10 徽章与状态标签 Must

统一为 pill 容器加 12px 文字：正常、运行中、运行中需关注、未运行、已拒绝、已恢复、未知。前端不再用 `.pill.g/.r/.y/.n` 四套手工色值，改为按语义名映射 token。

#### DR-11 空状态规范 Must

所有列表型组件必须实现三态空，且文案能区分：

| 类型 | 判定 | 展示 |
|---|---|---|
| 无数据 | 采集尚未开始或链路断开 | 图标 + 「尚未开始采集」+ 一句原因 + 重试或等待按钮 |
| 无内容 | 采集正常但确实没有 | 图标 + 「当前没有占显存的进程」+ 允许开任务的肯定信息 |
| 无权限 | 采集失败或权限不足 | 图标 + 「需要 root 才能看到端口归属进程」+ 提权说明 |

已知三处必须改：占显存的进程、已建立的外部连接、告警记录。

#### DR-12 加载态与骨架屏 Must

1. 首屏 6 张卡片用骨架条占位，替代当前的「—」。
2. 图表加载时用等高骨架块 + 「正在加载历史数据」。
3. 刷新时保留旧值，只在卡片右上角加一个细微的更新指示，不整屏闪烁。

#### DR-13 陈旧态与错误态 Must

1. 陈旧态保留数值可读，改为 `opacity: .75` 并保留饱和度，禁止 `.saturate(.4)`。
2. 顶部固定一条状态横幅，明确区分三种情况：面板后端无响应、SSH 采集链路断开、全部正常。
3. 横幅必须给出距上次更新的秒数与建议动作。
4. 错误态提供重试按钮，不能只显示一句文本。

#### DR-14 Toast 队列与执行反馈 Must

1. Toast 改为栈，最多同时 3 条，超出向上堆叠，4 秒自动消失，支持手动关闭。
2. 动作结果改为就地反馈：在触发行内显示状态徽章，在行下方展开可折叠的结果文本。
3. 进程页的动作不再强制跳转到服务页；服务页的输出区独立保留。
4. 确认弹窗必须展示将要执行的真实命令或影响面，包括服务名、命令、被影响资源、是否可逆。

#### DR-15 审计与告警列表改为结构化行 Must

1. 告警记录：时间列 + 级别徽章 + 规则名 + 触发值与阈值 + 持续时长 + 状态，操作列提供定位到该时刻的入口。
2. 操作审计：时间列 + 主机 + 动作类型图标 + 目标 + 结果徽章 + 耗时，输出文本折叠在展开行。
3. 采集健康：拆成 4 个独立字段块，状态、样本数、重连次数、延迟各占一格，不要拼成长串。

### 5.4 图表规范

### 5.6 数据链路前置条件

以下不是界面需求，但界面按目标形态落地必须后端配合，否则做不出效果。

#### DR-25 修复中文路径变问号 P0

根因已定位：`collector.sh` 第 11 行 `export LC_ALL=C` 使 procps 的 `ps` 在 C locale 下把每个非 ASCII 字节替换成 `?`，4 个汉字变 12 个问号。jq 与 PowerShell 环节均无问题，已在 192.168.3.3 上逐段复现验证。

修复：

```bash
# collector.sh 第 11 行
-export LC_ALL=C
+export LC_ALL=C.UTF-8
```

服务器已确认存在 `C.utf8` 与 `zh_CN.utf8`。若目标机器无 UTF-8 locale，需退化为 `LC_ALL=C` 并接受该缺陷，或在采集端改用 `/proc/*/cmdline` 直读绕开 `ps`。

同一行还影响 `df` 的中文挂载点名与 `hostname`。

验收：重新采集后，PID 2533235 的 cmd 字段应显示 `中间产物/清洗流水线_20261113/preprocess_idem_twin.yaml`。

#### DR-26 下发告警规则到前端 P0

`/api/boot` 当前不返回 `alerts`。需要下发规则 id、metric、op、threshold、level、text，使前端能：

1. 渲染告警规则表，让用户知道系统在盯什么。
2. 在图表上画阈值参考带。
3. 在卡片上解释「为什么这条在预警」。
4. 展示当前值与阈值的距离。

#### DR-27 区分端口归属的「无权限」与「无进程」 P1

`ss -tlnp` 需要 root。采集器需要区分三种情况并显式上报：有归属、无进程、权限不足不可见。当前一律显示「无进程信息」属于误导。

#### DR-28 多卡 GPU 支持 P1

`collector.sh` 第 27 行的 `head -1` 只取第一张卡。需要改为遍历全部 GPU，输出数组，并让 GPU 主卡支持纵向子卡列表。

#### DR-29 采集上限与标题口径对齐 P1

`procs` 采集上限 1500 条，但界面标题写「服务器全量进程」。需要在超限时显式标注「已截断，共 N 条，展示前 1500 条」，或提高上限。

#### DR-30 推送替代轮询 Should

服务器 3 秒一采，前端 2 秒轮询快照，1/3 的轮询是重复数据。建议 hub 提供 SSE 通道，样本到达即推送，同时消除轮询延迟。

### 11.2 对应需求与落地

- **DR-37 自报失败必须如实上报**：新增 `Get-FailMark`（大小写敏感匹配 `FAIL:/ERROR:/ERR:/WARN:`，避免误伤远端小写 `warning:`）。`svc_start`/`svc_stop` 与 `kill`/`kill9` 在 `rc=0` 但命中标记时返回 `ok=false` + `error`，审计记为 `self_fail:<MARK>`。`svc_log` 是只读动作，日志正文里的 FAIL/ERROR 不代表读取失败，明确排除在外。
- **DR-38 反馈三处一致**：Toast 颜色与文案一律跟随 `ok`；结果区同时呈现 `error` 与远端原文；进程行内 pill 由含糊的「警告」改为事实性的「未结束」。
- **DR-39 参数注入面收紧**：`sshHost` 用 `^(?!-)[A-Za-z0-9_.@-]{1,128}$`、`id` 用 `^(?!-)[A-Za-z0-9_-]{1,32}$`，面板、action worker、前端三处校验保持同构，避免「界面放过、后端拒」的错位体验。
- **DR-40 配置单次落盘**：`update` 先在内存中算完（含 activeHost 迁移），再一次 `Save-Config`。
- **DR-41 后端补长度校验**：`sub` ≤ 120 字符。
- **DR-42 列表幂等渲染**：状态未变化时不重建 DOM，保住焦点、滚动与可点击性。
- **DR-43 孤儿状态回收**：面板启动时（且仅在确认自己是唯一实例时）清理 `state/` 下未知主机的四类文件；`history/` 归档按设计保留。

### 12.3 被证伪的假设（没有据此改代码）

### 13.2 对应需求与落地

#### DR-50 纯标量数组/对象折回单行

新增 `Format-CompactJson`，在写盘前把「纯标量」块折回一行。安全红线：

- 仅当开括号独占一行、**每一个**成员行都匹配纯标量字面量、闭括号独占一行时才折；
- 任何一行不合规范（嵌套对象/混合内容）→ 整块原样保留，宁可少折不改语义；
- 折出来超过 200 字符也不折（可读性优先于短 diff）；
- 数组不加内边距 `[…,"…]`、对象保留 `{ … }`，贴合作者现有写法。

实测效果：一次完整主机增删改循环后，config.json 的 diff 从 **93+/20-** 降到 **6+/12-**，剩下的仅为作者手写的空行分隔与列对齐空格，属序列化器不该去猜的部分。

#### DR-51 折叠器单测

`build/test-jsonfold.ps1` 从 `panel.ps1` 抠出函数体直接跑，10 项断言：

- 每条用例都先做**双向解析语义比对**（折叠绝不能改变 JSON 含义）；
- 危险串专项：元素内含 `]`、逗号、转义引号、`{}`、反斜杠路径，均不得把扫描器带偏；
- 结构专项：外层含对象/嵌套数组时外层不折（内层纯标量可折）；
- 幂等专项：`fold(fold(x)) == fold(x)` —— 配置会被反复保存，不幂等就会逐次漂变；
- 真实 config.json 全量往返 141 → 62 行且语义不变。

本轮两次 FAIL 均为**测试自身预期写错**（先是把「外层不折」错声明成「整块行数不得减少」，后是把正则锚点 `$` 当字面量传给了 `Contains`），代码行为正确，已改断言粒度面非改代码。

### 15.2 对应需求与落地

#### DR-54 全量门禁单一入口

`build/gate.ps1`：依赖探测（pwsh / 面板 / node）+ 逐套运行 + 汇总表格 + 固定退出码：

| exit | 含义 |

| 2 | 有门禁因缺依赖**未执行**——明确不是通过，并提示先起面板 |

#### DR-55 未执行不等于失败（统一成 exit=2 约定）

门禁脚本自己区分三态：静态检查可跑而服务端不可达时，打印 `SKIP` 并 `exit 2`；gate 识别 2 并计入 BLOCKED。实测：面板停摆时 `pass=3 FAIL=0 BLOCKED=3~4 exit=2`；面板恢复后 `pass=7 FAIL=0 BLOCKED=0 exit=0`。

## 19. v4.2 第九轮迭代（启动器解析期死亡）+ 死规则识别

### 19.1 用户可见故障：打开 BAT 不弹网页（R-78，P1）

现象：双击「启动-服务器管家v4.bat」后无任何窗口 —— 没有面板页、连就绪探针的红字诊断窗都没有；`log/panel-run.log` 无新记录，48732 不监听。

定位链（每条都由观测排除，不是猜测）：
1. 字节检查 BAT：CRLF=15、裸 LF=0、无 BOM → 「LF 行尾导致 cmd 误解析」被自己否掉；
2. 原样字节复制到临时目录再跑：`cmd rc=255`、stderr 只有一句「此时不应有 is。」、stdout 为空 —— **整份 BAT 在 cmd 解析阶段就死了**；
3. 最小复现：`if 0 neq 0 (` + `echo x (pwsh) is required.` 的多行块**必炸**（rc=255），而只含带圆括号/含 if 字样的注释行则正常 —— 定位到「echo 文案里的圆括号破坏 if 块的括号配对」，残余的 `is required.` 被当成命令，于是报「此时不应有 is。」。

机制后果：解析期死亡发生在 `start … panel.ps1` **之前**，所以面板从未启动 → 无转录、无端口、无 Edge profile（实测 Edge 专属 profile 自 11-13 后没再被碰过）、探针也来不及触发。用户看到的就是「双击没反应」。

根因归属：这是我们自己在「加就绪探针防静默失败」那次改动里引入的回归 —— 把 echo 文案写进了 `if (...)` 多行块并带了圆括号。修故障时制造了另一个故障，值得写进教训：**BAT 里的 echo 文案禁止出现圆括号（尤其在 if 块内）；多行 if 块尽量改 goto 结构**。

DR-78 落地：
- BAT 重写为 goto 结构（`if errorlevel 1 goto nopwsh`），echo 文案不再带任何圆括号，字节级写盘（CRLF、纯 ASCII）；
- 新增 `build/test-launcher.ps1` 门禁（静态 + 功能双层）：
  - 静态：纯 ASCII、CRLF 行尾、echo 行不得带圆括号；
  - 功能：把 BAT 原样复制到临时目录跑一遍，要求 `cmd` 执行到底且 rc=0。复制到临时目录可避免真的拉起面板与探针（零副作用）；
  - 反证有效：注入「if 块内 echo 带括号」的坏副本 → rc=255，门禁判 FAIL；真实文件 → PASS。
- 全链路实证：修复后按双击方式执行 → panel 拉起、48732 监听、`boot ok`、Edge 应用模式窗口带着 `ServerPanelV4Edge` profile 真正开出（主进程 + 子进程组）。

### 19.2 告警规则可信性：死规则识别（R-79，P1 潜在）

原有缺陷：`Eval-Alerts` 里 `$v = $sc[$r.metric]; if ($null -eq $v) { continue }` 把「这台机器暂时没这个数据」和「指标名从来没出现过」混为一谈。指标名写错（或引用了未配置的 `service.xxx`）的规则将**永远不触发且毫无痕迹** —— 用户恰恰是靠告警发现过热/满盘的，静默失效比误报危险。

DR-79 落地：
- agent：`alertSt[rule]` 增加 `miss` 计数；`$sc.ContainsKey($r.metric)` 时清零，否则累加。连续 20 个样本仍取不到键才判死，避免刚起流时误报；落盘沿用既有 `alertSt` 通道。
- panel：`/api/status` 每台主机增加 `deadRules`（id + miss）。注意 OrderedDictionary 必须**按键赋值**（`$e['deadRules'] = …`），点号赋值只改适配器成员，`ConvertTo-Json` 时会被吞（本仓库已两次踩到）。

## 21. R-82：进程表 CPU% 口径说明（2026-11-20，用户反馈「两个进程都显示 100%，是不是有问题」）

用户疑问属实但结论相反：**不是缺陷，是与 top/htop 完全一致的业界口径**。

### 21.1 事实核查

- `collector.sh` 的进程 CPU 直接取 `ps -eo ... pcpu`——Linux ps/top 的约定是**一颗逻辑核吃满记为 100%**，多线程进程会显示 >100%（如 4 线程各跑满 → 约 400%）。
- 本机实测：20 逻辑核、负载 6.58/6.82/7.01；同时有 6 个 joblib/loky 工作进程各显示 99.5%、99.4%、99.3%、99.1%、98.4%、98.3%——每个 worker 各占满一颗核，负载合计恰好≈6.5，完全吻合。
- 对照口径：`derived.cpuPct` 是按全部 20 核归一的整机占用（当前 31%），两套口径并存、互不相同是设计使然。

### 21.2 修复

`dashboard.html` 进程表「CPU%」表头补 title tooltip，明确写出「单核为 100%、多线程可 >100%、本机 20 核满载时上限 2000%」，
避免把「一核吃满」误读成「整机打满」。保持与 top 一致不变（若改全机口径反而破坏与 `top`/`htop` 的对照）。

### 21.3 教训

多核机器上「两个 100%」完全正常；排查这类疑问时应先看 `nproc`、`load average` 与各进程值之和，而不是先怀疑面板。

### 22.5 连带发现并修复：双启动防护被 http.sys 双队列绕过（R-84）

排查噪音时做了个实验：主实例存活期间再拉一个隐藏实例。新实例**照样绑定成功、照常 `PANEL-READY`**，结果双写 `hub.json`、双起 agent（对远端开两条 SSH 流）。根因：Windows http.sys 允许多个 HttpListener 同时注册同一前址，旧逻辑「`listener.Start()` 失败 → 探测 `/api/boot` 判已有实例」在本机永不触发。

修复：改用命名内核互斥体 `Global\ServerPanelV4-<port>`（置于 `Start-Agents` 之前）。重复实例 `WaitOne(0)` 立即失败即退出（顺带为现有实例开窗）；上代崩溃遗留的 abandoned 锁由内核自动接管，不误伤重启。

### 22.7 用户反馈「打开 BAT 先弹 Edge 又弹一个程序窗，程序没在 Edge 上显示」（R-86，2026-11-22）

用户问「为什么先弹 Edge 再弹程序窗，利用 Edge 了吗，程序没在 Edge 上显示」。取证结论：

1. **Edge 应用模式窗口就是程序本体**：`panel.ps1` 内嵌 HttpListener 在 `127.0.0.1` 提供 dashboard.html/app.js，随后以 `msedge --app=<url>` 开窗（无标签栏地址栏的独立外观）。窗口标题即页面 `<title>`（服务器管家 v4），实测根页 30961B、app.js 55279B、快照返回真实 GPU 数据——界面确实在这个 Edge 窗口里，只是借 Edge 当渲染壳：专用隔离 profile `%LOCALAPPDATA%\ServerPanelV4Edge`，不碰日常浏览数据；全部回环不出网；CSP 锁死 `script-src 'self'`；无 Edge 时回退默认浏览器，`-NoBrowser` 可完全不开窗。
2. **空白 Edge 窗的真正成因（本轮逐层实测定位）**：Windows 上 http.sys 双队列（R-84）曾让重复实例都绑得上端口；而上代强杀会在专用 profile 留下脏会话数据，使下一次 `--app` 启动「起了一整个 Edge 栈（16~21 个进程）却建不出初始目标窗口」，屏幕上只剩一个**标题为空的空白 Edge**。旧守卫用「命令行带 ServerPanelV4Edge」当身份特征，把这个空白窗（句柄非空+特征命中）误判成有效面板，于是既不叠窗也不重试——双击后用户有时看到「一个服务器管家 + 一个空白 Edge」，有时什么都看不到。转录日志里的 `WIN-OPEN ok` 与外部标题统计 0 的矛盾正是这一假阳性的直接证据。
3. 修复（R-86 终版，三段）：① `Find-PanelEdgeWindow` 收窄为纯页面标题匹配（与外部诊断同口径，归零误伤）；② `Open-PanelWindow` 每代开窗前 `Reset-PanelEdgeProfile` 整体清掉可弃 profile（脏会话从根上消失），并用「进程命令行出现 `--app=URL`+专用 profile」验证启动被接受，最多重试一次，仍失败兑底默认浏览器；③ 重复启动（含互斥体失败分支与端口占用回退分支）一律只聚焦现有面板窗，绝不再开第二个。
4. **本次取证现场还暴露了调试纪律问题**：门禁验证时在命令内拉起的带界面实例没有随会话结束清理，残留在了用户桌面上（用户当时看到的两个窗口里有我留下的残留）。门禁脚本自身一律 `-NoBrowser`（日志实证），但人工验证启动必须收尾清理——已在本轮修复流程中强制执行（每次验证末尾清场，残留计数归零作为断言项）。

验证：同一会话内清场→首启→标题窗口 ≤11s 出现（WIN-OPEN ok）→立刻重复启动→窗口数仍为 1、`DUP-FOCUS:YES`、原实例 pid 不变；全量门禁 13/13。

### 22.6 用户定夺：默认语义改为「采集活着就不退出」（R-85，2026-11-22）

R-83/R-84 只让链路「不死得不明不白」，关窗后 90 秒整机照旧消失。用户在二选一里明确选「采集活着就不退出」。实现：`idleLimit` 重新定义为「采集全部停摆后、纯空闲多少秒才退出」，缺省 `-1`=常驻；空闲判定前先看所有主机的 meta——有任一主机 `running=true` 且 `ageSec<30` 即视为采集中，绝不退出。想恢复旧的省资源行为：config.json 显式写 `idleExitSec=<秒>` 或启动加 `-IdleSec=<秒>`（`-IdleSec -1`=常驻，`-IdleSec 0..9` 仍走旧式纯空闲）。同日把用户本机 config.json 的 `idleExitSec` 由 90 改为 -1，保持运行态与新语义一致。

## 22. R-83：「长时间运行就断线」根因与加固（2026-11-22，用户反馈「为什么长时间运行会断线」）

### 22.1 结论先行

**不是 SSH 长连接守不住，是整条链路的存活被「有没有浏览器在轮询 HTTP」这一个信号单点决定。**

SSH 会话层本身有完整自愈：客户端 `ServerAliveInterval=15 × CountMax=3`（≤45s 感知死链）→ agent 指数退避重连（1s→15s 封顶）→ 面板 700ms 巡检兜底拉起。网络抖动只会产生短暂红字「采集已中断」，不会演变成永久离线。

真正致命的是空闲退出链（`config.idleExitSec=90`，BAT 不传 `-IdleSec`）：

1. `panel.ps1` 的 `$script:lastActive` **只在收到 HTTP 请求时刷新**（主循环里 `/api/*` 处理完之后赋值）；
2. Edge 应用窗口开着时每几秒轮询，关窗/最小化节流/机器睡眠后轮询停掉；
3. 90 秒无任何请求 → 主循环空闲分支 `break` → 收尾调 `Stop-Agents` 把每个 agent 的进程树 `taskkill /T /F` 一并带走 → `PANEL-EXIT`。

于是 hub + 全部 agent + SSH 流整体消失，且 agent 没有机会写自己的 `exitReason='idle_heartbeat_lost'`（被父进程强杀）。用户看到的就是「跑着跑着断线」，重开又要双击 BAT。

### 22.2 证据（2026-11-22 实查）

- `log/panel-run.log`：本轮面板 11:41:03 启动、12:09:59 `PANEL-EXIT`，存活 28 分 56 秒——恰在用户停止交互约 90 秒后退出，全程无终止错误转储，干净退出而非崩溃。
- `state/hub.json` 停在 ts=12:09:59；`meta-gpu3090.json` 最后样本 12:09:58（ageSec=1）、`exitReason` 为空、`restarts=0`——均指向被强杀而非会话中断。
- `history/` 目录仅有 11-13/16/18/19/20/22 六个文件：**从未成功跨夜运行过一次**，每天的会话都是「用一段、停一段」。
- `state/alerts-gpu3090.json` 中 `agent` 键当前无任何告警记录——排除「频繁 SSH 掉线」作为长期症状。

### 22.3 修复（三处，工程级、不改空闲语义）

1. **挂起/大间隔宽限（R-83）**：主循环拍长 ~0.7s，任一拍发现墙钟比上一拍漂过 10s（睡眠/挂起/长卡顿的恢复信号），重置 `$script:lastActive` 并留痕。此前 Windows 从睡眠恢复时墙钟跳变 ≫90s，恢复瞬间就被空闲判定当场收走——这是「跑很久突然断」的另一常见形态。
2. **退出留痕**：`PANEL-EXIT` 前往 `log/panel-run.log` 追加一行 `时间 PANEL-EXIT why=<idle|空> sinceActive=<Ns> pid=<pid>`。此前只打裸 `PANEL-EXIT`，事后无法回答「为什么没了」。
3. **BAT 支持常驻透传**：系统设 `SP_IDLE=-1` 再双击，启动器把 `-IdleSec %SP_IDLE%` 传给面板（`if defined SP_IDLE`），无人值守 7×24 不用命令行。纯 ASCII/CRLF 契约不变，launcher 门禁覆盖。

### 22.4 教训

单活性信号设计（轮询即心跳）在「面向人的本地工具」里省事，但只要存在无人值守诉求，它就是整条链路的最短板：关窗、睡眠、最小化节流每一个都算「断开」。要么明确文档化「无人值守必须 `-IdleSec -1`」，要么把空闲语义改成与采集状态双因子（采集活着就不退）——后者是产品决策，等用户定夺。

## 22.8 R-87 双窗终因与开窗加固（第十五轮，2026-11-22）

### 22.8.1 现象与用户假设

用户反馈「一次性起来两个窗口」（一扇面板 + 一扇空白/异常 Edge），并怀疑日常 Edge 的 WeTab 扩展导致面板起不来。

### 22.8.2 取证结论

1. **WeTab 不是直接原因**：面板用独立专用 profile（`%LOCALAPPDATA%\ServerPanelV4Edge`），与日常 Edge 完全隔离。实测新建的专用 profile 只含 Edge 预装组件扩展（Scholarscope / Zotero Connector / Forest / Edge relevant text changes 等 17 个，均带 `microsoft_install_signature`，**不含 WeTab**）。WeTab 只存在于用户的日常 profile，无法直接进入 `--app` 会话。
2. **当日实况**：`log/panel-run.log` 显示 16:35:02 与 16:35:34 两个实例先后各自 `WIN-OPEN ok`。当前代码下（A 存活时第二发必被互斥体拒绝，毫秒级竞态同样被拒，已多次实证）双开只可能发生在「第一实例已死、互斥体已被内核释放」到第二发启动之间的窗口期——第一实例在没有任何 `记录停止` 标记的情况下消失（进程树被外部回收）。互斥体保护的是「活着的第一实例」，管不住「第一实例先死」。
3. **「窗口迟迟不出现」的三个放大因素**：
   - 旧 WIN-OPEN 成功判据只看「--app 进程存在」，不看「真实带标题窗口」——进程起了、窗口还没建出来时就报 ok，重复启动撞上该中间态就可能叠窗；
   - 专用 profile 每代新建都会被 Edge 复制一整盒预装扩展，个别扩展会在启动瞬间抢占标签页/改写窗口标题（实测采样中出现过 `Ghelper Settings`、`无标题` 之类的中间标题）；
   - 轮询热路径每次都做全机 `Win32_Process` 枚举，高负载下单次数百毫秒，检测被拖慢，又反过来增加撞中间态的概率。

### 22.8.3 修复（R-87，panel.ps1 为主）

1. **开窗一律加 `--disable-extensions`**：`--app` 面板页不需要任何扩展，从根上排除扩展干扰与标题抢占。
2. **WIN-OPEN 两阶段判据**：阶段 1（≤5s）只验证 `--app` 进程被接受（没起或秒退立即换代重试）；阶段 2（≤30s）用轻量轮询等真实带标题窗口出现；两阶段都失败才兜底默认浏览器打开——保证双击后每次都看得见面板，且不打断健康栈的自我拆台不再发生。
3. **新增轻量函数 `Find-PanelEdgeWindowFast`**（只按窗口标题匹配，不枚举全机进程）用于开窗热路径。
4. **转录分文件（R-87b）**：每实例写自己的 `log\panel-run.<pid>.log`，多实例（含被互斥体拒掉的重复启动）并发写同一文件会把转录搅成乱序/残缺（本轮排查亲眼所见）。`PANEL-READY`/`RESUME-GAP`/`PANEL-EXIT` 等生命周期标记仍由持锁的唯一实例单写 `panel-run.log`；launch-probe/restart 的日志引用改为取最新一份 `panel-run*.log`。
5. **拒绝分支僵尸窗清理（R-87c/f）**：重复启动找不到有效面板窗、但存在创建超过 60s 的专用 profile 老栈时清掉 profile，避免桌面留点不开的幽灵窗；所有权查询失败时用「机器上有专用 profile 栈 + 标题命中」兜底，并加重试以提升置前台成功率。

### 22.8.4 验证

- 语法：`build\syntax-check.ps1` 31 文件 0 错。
- 行为（同条命令内完成并清场）：冷启动标题窗 **≤1s** 出现；A 存活时双击第二发 → 面板进程数 1、窗口数 1、`PANEL-ALREADY-RUNNING`、第二实例静默退出；间隔 106ms 的竞态双发 → 仍然只有 1 窗；收尾断言残留面板=0、agent=0、Edge 栈=0。

## 22.9 R-88 / R-89 孤儿采集与窗口生命周期（第十六轮，2026-11-22）

### 22.9.1 现象

用户连续反馈三件事：Edge 起来后数据不正常、页面显示「SSH 采集链路断开 · 显示最后已知值」、
随后「面板后端无响应」反复出现。

### 22.9.2 取证结论（三层原因）

1. **孤儿 agent**：hub 被杀/被回收后，其 agent 不随之退出，继续写 state（实测一次孤儿在 hub
   死后又采集数分钟）。下代 hub 拉起时不清理，会双写 `latest-/meta-/rollup-<id>.json`。
2. **窗口归属误判**：`Open-PanelWindow` 原以「标题命中」认已有面板窗，用户日常 Edge 里恰好
   开着同名旧标签页时（历次兜底用默认浏览器打开留下的），专用 `--app` 窗永远不被创建——
   用户看到的始终是旧标签页。数据源没问题，看起来却像「Edge 起不来」。
3. **冷启动慢**：每代开窗前整个删除重建专用 profile，Edge 每次从零初始化 user-data-dir，
   启动几十秒，期间桌面只有「URL 主机名 + 转圈」的加载态，用户以为坏了。
4. 本轮「后端无响应」的直接诱因还包括调试侧反复重启/清场（验证纪律问题），已改为跨命令
   存活验证（WMI 创建实例可在命令边界存活，实测 pid 连续两拍存活、数据 age=1s）。

### 22.9.3 修复

- **R-88**（Start-Agents）：起新 agent 前按 `-HostId` 清理同主机的跨代孤儿 pwsh；本代已跟踪的活进程不动。
- **R-88b**：新增 `Find-PanelEdgeWindowOwned`（标题命中后再验证命令行带专用 profile），开窗前认窗一律走它；
  新增轻量 `Find-PanelEdgeWindowFast` 供开窗热路径轮询（无全机枚举）。
- **R-89a**：`Reset-PanelEdgeProfile` 只在起窗失败后的重试换代调用，常态复用既有 profile。
- **R-89b**：互斥体拒绝分支找不到可聚焦窗口时（用户关掉了 --app 窗但采集仍在跑，或空白僵尸栈），
  清僵尸栈后由本实例开一扇新窗再退出——保证每次双击后桌面永远恰好一扇可见面板窗；
  开窗函数块整体上移到互斥体分支之前（PowerShell 函数不跨执行顺序提升）。
